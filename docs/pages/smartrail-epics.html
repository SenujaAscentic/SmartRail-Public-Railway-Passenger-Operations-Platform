SmartRail Epic Breakdown

Twelve epics, organised by user goal rather than by app. Each story carries its app as a label, and stories in different apps are linked by the domain events one produces and the others consume. Features are capabilities from the MoSCoW list; technical layers (API, screens, events, audit, tests) appear as tasks inside every feature.

Epic (user outcome) → Feature (MoSCoW item) → User story (acceptance criteria, app label) → Tasks (build work)
Must in the MVP Should if time allows

IDs refer to define/moscow.md (features) and define/user-stories.md (stories). Tasks are high level; detailed tasks are written at the start of each build day.

Event catalogue (draft)

The events are the contracts between apps. Names are past tense: something that has already happened. This is the first draft; payloads and versioning are fixed in the domain model step.

Dashed = integration event sent to the external catering provider (signed webhook), not on the internal stream.

  • US-B5 delivers every internal event to the apps over one stream (SSE); US-B6 decides which consumers get each one (propagation matrix).
  • US-O10 records every event a controller or station manager produces in the audit log.
  • Plan data (timetable, roster, menus, hotline) is read through APIs, not events: US-D4 caches the day timetable, US-C1 the roster, US-F3 the provider menus.
  • Each consumer story is built and tested against fixtures of the event, so an app can be built before the producer's screen is finished.
