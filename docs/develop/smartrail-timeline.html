    Every day, not at the end

    • AI usage log. Record the tool, the prompt, what you accepted, what you rejected and why. Section 23 asks for this, and it cannot be rebuilt from memory on 19 October.
    • Security. The threat model is done on 8–9 October. Each build day then adds its controls (auth, input validation, rate limits), as section 17 requires.
    • Tests alongside code. Write unit and API tests on each build day. The QA days at the end are for the 5 end-to-end flows, defects and the quality assessment.
    • Decision records. Write a short ADR whenever you choose a technology or reject an AI suggestion.
    • Commit daily with clear messages. The git history is evidence of your process.

    If you fall behind, cut in this order

    1. Could items are already out of the plan: station terminal, fares, one-change journeys, waiting-area display, shift handover note.
    2. Should items first: guest mode, Emergency button, network incident banner.
    3. Station manager notices and closure request.
    4. Text-to-speech on the large screen (keep the visual announcements).
    5. One incident applied to many journeys; staff two-factor login.

    Never cut: the discovery and requirements artifacts, the AI usage evidence, the threat model, the 5 automated E2E flows, the catering integration required by section 23, and the deferred-scope list.
